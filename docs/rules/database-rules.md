## 1. 设计流程与通用约定

### 1.1 设计流程与产出物

数据库设计按四个阶段推进，每一步都有明确产出，不得跳步：

| 阶段 | 输入 | 产出 | 完成标志 |
|---|---|---|---|
| 概念模型 | PRD 第 8 章、01 模块职责 | 实体清单 + 关系说明（不落字段类型） | 与 PRD 实体一一对应，多/少都要说明 |
| 逻辑模型 | 概念模型 + 业务规则 | 表清单、字段清单、主外键关系、枚举取值表 | 每条业务规则能找到承载它的表或字段 |
| 物理设计 | 逻辑模型 + 本规范 | 类型、长度、索引、约束、注释完整的 DDL 草案 | 通过第 15 章 DDL 评审清单 |
| 迁移落地 | 物理设计 | Flyway 脚本 + 回滚说明 + 种子数据（如需） | 空库全量执行通过 |

规则：

1. 每个阶段产出都需评审后才能进入下一阶段。
2. 物理设计阶段不接受口头结论，字段、索引、约束必须写进文档或迁移脚本。
3. 概念/逻辑模型的任何变更都要回写 PRD 第 8 章，不允许文档与实现漂移。

### 1.2 通用约定

1. 一切结构变更必须通过迁移脚本落地，禁止手工在生产库执行 DDL/DML。
2. 表必须有注释，字段必须有注释（含枚举取值含义）；注释用中文。
3. 同一语义的字段在全库必须同名同类型，不允许一处 `status` 一处 `state`。
4. 所有表必须可回答三个问题：谁创建的、什么时候创建、什么时候最后修改。
5. 字段增删必须能回指到 PRD 条目；PRD 未定义的表或字段，先提建议再落地。
6. 不预埋未被需求使用的字段（"以后可能用得上"不是理由）。PRD 已明确移除的字段（如题目难度）不得重新出现。
7. 冗余字段只在两种情况下允许：快照（如面试会话的 `stage_name`）或经过评审的性能优化，且必须注释说明"为什么冗余、由谁维护"。

## 2. 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 表名 | 小写 snake_case，单数名词 | `subject`、`learning_path`、`practice` |
| 关联表 | `{主表}_{从表}`，按语义顺序 | `student_path` |
| 字段名 | 小写 snake_case | `stage_id`、`correct_rate` |
| 主键 | 统一 `id` | `id` |
| 外键 | `{被引用表单数}_id` | `subject_id`、`practice_id` |
| 布尔 | `is_` / `has_` 前缀 | `is_correct`、`is_degraded` |
| 时间 | `_at` 结尾 | `created_at`、`finished_at`、`expire_at` |
| 计数 / 比率 | `_count` / `_rate` | `question_count`、`correct_rate` |
| 快照字段 | 原字段名 + 语义后缀 | `stage_name`（会话快照） |
| 索引 | `idx_{表}_{字段}`；唯一 `uk_{表}_{字段}` | `idx_answer_practice_id`、`uk_student_phone_hash` |
| 迁移脚本 | `V{序号}__{动词}_{对象}.sql` | `V003__create_practice_tables.sql` |
| 迁移回滚说明 | 同目录 `R{序号}__{同描述}.md` 或脚本内注释 | `R003__create_practice_tables.md` |

禁止：拼音命名、`tbl_` 前缀、字段名与保留字冲突（`order`、`key`、`desc`、`status` 需换名或加限定）、同一含义出现 `student`/`user` 混用（本项目学员统一 `student`，后台用户统一 `admin_user`）。

## 3. 主键与必备字段

1. 主键统一 `BIGINT UNSIGNED AUTO_INCREMENT`，不使用业务字段做主键。
2. 每张表必备：`id`、`created_at`、`updated_at`。
3. 内容与配置型表（学科、路线、阶段、课程、题目、能力维度、面试难度）额外必备：`created_by`、`updated_by`（`admin_user.id`），用于操作日志与追责。
4. 需要乐观并发的表（`practice`、`course_progress`、`interview_session`、`interview_quota`）加 `version INT NOT NULL DEFAULT 0`。
5. 不使用 `SELECT *`；不使用复合主键（关联表用自增 id + 唯一索引约束业务唯一性）。
6. 自增主键不得作为对外可枚举的业务编号使用；如需对外编号，另设业务编号字段。

> **变更记录**：原第 3 条含"面试主题"，PRD v1.0 与 01 v1.0 已删除面试主题模型，此处已替换为「面试难度 InterviewDifficulty」（全局配置：名称、启用状态、难度描述、考察重点，见 PRD 8 章）。

## 4. 数据类型

| 语义 | 类型 | 说明 |
|---|---|---|
| 时间 | `DATETIME(3)`，存 UTC | 不用 `TIMESTAMP`（2038 与隐式时区转换） |
| 业务日期（如配额归属日） | `DATE`，存 `Asia/Shanghai` 日期 | 与 UTC 时间列区分开，见第 9 章配额条 |
| 状态 / 枚举 | `TINYINT UNSIGNED` + 注释里的取值表 | 不用 MySQL `ENUM`（改值要 DDL） |
| 布尔 | `TINYINT(1)` | 与状态字段区分，不复用 |
| 正确率 / 得分 | `DECIMAL(5,2)` 或 `TINYINT UNSIGNED`（0–100） | 明确量纲并写进注释，不用 `FLOAT` |
| 计数 | `INT UNSIGNED` | 不用字符串存数字 |
| 长文本（题干、解析、参考答案、总评、转写文本） | `TEXT` / `MEDIUMTEXT` | 列表查询不得返回 |
| 手机号 | `VARCHAR(20)` | 存储策略见第 11 条与 Q18 |
| 密码 | `VARCHAR(100)` 存哈希 | 禁止明文、禁止可逆加密 |
| 头像 / 封面 | `VARCHAR(512)`（OSS key 或 URL） | 存 key 优先，展示时签名 |
| 课程链接（B 站） | `VARCHAR(512)` | 超长改 `TEXT` |

1. 字段显式 `NOT NULL` 并给默认值；只有确实需要"无值"语义时才允许 `NULL`（如注销后释放的手机号）。
2. 字符串长度按实际业务上限设定，不用 `VARCHAR(255)` 一把梭。
3. 禁止用 `0` 或空字符串表达"未设置"，与真实值区分开。
4. 布尔字段禁止用 `NULL` 表示"未知"，需"未知"时改用状态字段。

## 5. 约束与索引

1. 业务唯一性必须由数据库唯一索引保证，不能只靠应用层判断（并发下必然击穿）。
2. 不建物理外键（FK），但**每个外键列必须建索引**；引用完整性由应用层 + 迁移脚本保证。
3. 联合索引遵守最左前缀；按 `WHERE → ORDER BY → SELECT` 顺序设计，优先覆盖高频查询。
4. 区分度低的列（状态、布尔）不单独建索引，作为联合索引的后缀。
5. 单表索引数控制在 5 个以内（不含主键与唯一索引），新增索引必须说明对应查询场景与预期收益。
6. 禁止在索引列上做函数运算或隐式类型转换（`VARCHAR` 列不得用数字查询）。
7. 模糊查询禁止左模糊 `%xxx`；需要搜索时给出方案（前缀索引 / 全文索引 / 外部检索），不得默认上线全表 `LIKE`。
8. 深分页（`OFFSET` 超过 1 万）必须改为游标分页（`WHERE id > ? ORDER BY id`）。
9. 唯一索引务必考虑软删除与状态语义：需要"删除后可重建"的表，唯一索引要么带状态列，要么允许 `NULL` 参与（MySQL 唯一索引允许多个 `NULL`）。

**必须存在的唯一约束（最小集）**

| 表 | 唯一键 | 依据 |
|---|---|---|
| `student` | `uk_student_phone_hash(phone_hash)` | 注册唯一；注销时 `phone_hash`/`phone_cipher` 置 NULL，释放手机号 |
| `learning_path` | `uk_learning_path_subject(subject_id)` | 学科与路线一一对应（PRD 4 章） |
| `student_path` | `uk_student_path(student_id, path_id)` | 同一路线不重复加入 |
| `course_progress` | `uk_course_progress(student_id, course_id)` | 完成标记幂等 |
| `wrong_question` | `uk_wrong_question(student_id, question_id)` | 错题唯一在册 |
| `answer` | `uk_answer(practice_id, question_id)` | 一次练习内每题一条作答 |
| `interview_quota` | `uk_interview_quota(student_id, quota_date)` | 每日次数原子计数 |
| `admin_user` | `uk_admin_user_account(account)` | 后台账号唯一 |

## 6. 软删除与状态

1. 题目**只停用不硬删**（PRD 6.4）；停用用状态字段表达，`question` 保留历史作答引用。
2. B 端用户、学科、课程、学习路线的"删除"一律用状态字段，不做物理删除。
3. 需要软删除的表可用 `deleted_at DATETIME(3) NULL`，但必须同步处理唯一索引（见 5.9）。
4. 学员注销（PRD 7.6）不是删除：手机号、昵称、头像置空或脱敏，记录以匿名 ID 保留，`status` 置为已注销。
5. 状态字段取值必须集中定义在一处（常量类或字典表），代码里禁止散落魔法数字。
6. 状态机只允许在服务层按显式流转表推进，数据库层不做状态约束（不用触发器/`CHECK` 兜业务状态）。

**本项目状态取值基线**

| 表 | 字段 | 取值 |
|---|---|---|
| `student` | `status` | 1 正常 / 2 禁用 / 3 已注销 |
| `practice` | `status` | 1 进行中 / 2 已完成 / 3 已作废 |
| `interview_session` | `status` | 1 创建中 / 2 进行中 / 3 正常完成 / 4 未完成 / 5 已过期 / 6 已作废 |
| `interview_report` | `status` | 1 正常 / 2 未完成 |
| `question` | `status` | 1 启用 / 2 停用 |
| `subject` / `course` / `learning_path` | `status` | 1 启用 / 2 停用 |
| `stage` | `status` | 1 启用 / 2 停用 |
| `dimension` | `status` | 1 启用 / 2 停用 |
| `wrong_question` | `status` | 1 在册 / 2 已移出 |
| `answer` | `judge_status` | 1 待判分 / 2 已判分 / 3 待自评 / 4 自评完成 |
| `import_job` | `status` | 1 处理中 / 2 全部成功 / 3 全部失败 |

## 7. 事务与并发

1. 事务必须短：禁止在事务内发起 HTTP 调用、短信、大模型、ASR/TTS、OSS 读写（与 02 §1.3 的"AI/短信/OSS 调用放在事务边界之外"一致）。
2. 简答判分（大模型）在事务外完成，判分结果回写单独提交；判分失败走降级，不阻塞练习提交。
3. 一次练习提交（写 `practice` + 批量写 `answer` + 更新错题本 + 更新掌握度口径）在同一事务内完成，保证数据一致。
4. 错题移出（任意一次答对）必须幂等：以 `uk_wrong_question` 兜底，重复移出不产生脏数据。
5. 课程完成标记必须幂等：`course_progress` 上 `(student_id, course_id)` 唯一，重复点完成只更新时间。
6. 面试会话与练习的状态流转用条件更新（`UPDATE ... WHERE status = 期望值`）防并发覆写，禁止"先查后改"。
7. 批量导入使用单事务，失败整批回滚（PRD 6.4、10）；导入任务状态另表记录，事务与任务状态分开提交。
8. 乐观锁表统一用 `version` 列，更新语句形如 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`，受影响行数为 0 视为冲突并提示重试。
9. 禁止长事务持有行锁等待外部接口；需要"占位 + 后续确认"的场景拆成两段事务。

## 8. 迁移与变更

1. 已执行的迁移脚本**永不修改**，变更一律新增脚本。
2. 每个脚本必须提供回滚说明（注释或同名 `.md`）；不可逆操作（删列、改类型、刷数据）需单独评审并在 PRD 变更记录里留痕。
3. 大表变更遵循"先加后改再删"：加新列（可空）→ 双写/回填 → 切读取 → 删旧列，禁止一步到位改类型或改语义。
4. 迁移脚本必须能在空库上从头执行成功（CI 校验），并保证幂等性说明（一次性脚本不接受重复执行）。
5. 结构变更完成后同步更新本文件第 2–6 章相关约定与 PRD 第 8 章概念模型。
6. 开发、测试、生产统一 MySQL 8.0；脚本按 8.0 语法编写，排序规则统一 `utf8mb4_0900_ai_ci`。
7. 种子数据（难度档位、预置角色）用独立脚本 `V{n}__seed_{对象}.sql`，可重复执行的用 `INSERT ... ON DUPLICATE KEY UPDATE`。

## 9. 本项目特定约束（对齐 PRD v1.0）

1. **内容模型固定为四层**：学科 → 学习路线 → 阶段 →（课程 / 题目）。不得引入"知识点"层，不得让题目跨阶段复用，不得引入课时/分 P 层（PRD 第 4 章）。
2. 学科与学习路线一一对应，`learning_path.subject_id` 唯一。
3. 一名学员同一时间只有一条主路线（PRD 5.3）：当前主路线记在 `student.current_path_id`；`student_path` 只记录加入历史，允许同一学员多条历史记录。
4. 掌握度取"最近一次阶段练习正确率"（PRD 7.2）：需按 `(student_id, stage_id)` 取最近一次练习，为此建联合索引；掌握度是计算结果，**不落冗余列**，除非后续出现性能问题并评审。
5. 完成度 = 已完成课程数 ÷ 课程总数（PRD 7.3）：由 `course_progress` 实时统计，不做冗余计数列。
6. 练习类型必须区分"阶段练习"与"错题重练"，错题重练的数据在完成度与掌握度统计中必须被排除（PRD 7.2、7.3）；统计 SQL 必须显式带类型过滤。
7. **能力维度属于学科**（`dimension.subject_id`），被面试报告使用（`report_dimension.dimension_id`）。**面试主题模型已删除**（PRD v1.0），不得再出现 `interview_topic` 表或 `topic_id` 字段；删除维度前必须检查是否被报告引用，只允许停用。
8. **面试难度**：`interview_difficulty` 为全局配置表（名称 简单/中等/困难、启用状态、难度描述、考察重点），不含 `subject_id`。Q29 已确认全局三档：**不新增 `subject_difficulty` 关联表，不给 `interview_difficulty` 加 `subject_id`**；“学科至少一个启用档位”按全局启用档位判断。
9. **面试会话阶段快照**：创建会话时确定并快照 `stage_id` + `stage_name`（冗余），中途切换主路线不影响已开始的会话；`stage_name` 不随阶段改名而更新，删除阶段不得影响历史会话（只停用）。
10. **面试每日次数（PRD 5.7 / 13 章第 21 条）**：每学员每天最多 3 次，**按 `Asia/Shanghai` 自然日**计算，不按学科/难度拆分，未使用不累积。落地要求：
    - 用 `interview_quota(student_id, quota_date DATE, used_count, version)` 承载，`quota_date` 存上海日期而非 UTC 时间，避免跨时区错位；
    - 占用必须**原子**（`INSERT ... ON DUPLICATE KEY UPDATE used_count = used_count + 1` 或条件更新），并发创建不得突破上限（PRD 第 10 章）；
    - 创建会话即计 1 次；正常完成/提前结束/未完成/已过期均计入；**系统或 AI 故障导致会话作废时返还次数**，返还操作必须幂等（以会话状态迁移为触发条件，不能重复减）；
    - 续答（24 小时内回到断点）不重复计数。
11. **面试消息只存转写文本**（PRD 6.5 / 02 §5.1）：不设音频字段、不落音频文件；`interview_message.content` 为转写文本，`round` 记录轮次（开场 1 + 追问 3）。
12. 面试会话过期时间显式落库（`expire_at`），过期判定以库内时间为准，不用前端时间。
13. 操作日志（`operation_log`）只追加，不允许更新与删除；含 IP，按时间分区或定期归档（保留期见 Q23）。
14. 注销学员的匿名 ID 必须与真实身份解耦，且不得通过关联表反推手机号。

## 10. 查询与性能

1. 所有列表接口必须有分页，`size ≤ 100` 在参数校验层强制。
2. 禁止 N+1：关联数据用批量查询（`IN`）或一次联表，不在循环里查库。
3. 禁止无条件全表扫描的统计：看板指标（PRD 6.10）需明确统计口径与索引支撑；P0 用实时 SQL，出现性能问题再按 Q19 引入汇总表，汇总表必须写明刷新策略。
4. 大字段（题干、解析、总评、转写文本）不在列表查询中返回。
5. SQL 上线前必须看过执行计划；出现 `filesort`、`temporary` 或全表扫描需说明原因并给出结论。
6. 统计查询单独定义在 Mapper XML 中，不复用通用 CRUD 方法，便于评审与优化。
7. 慢查询阈值与记录方式在部署阶段确定；开发期 SQL 必须能在 100ms 内返回（万级数据量基线）。

## 11. 安全与合规

1. 密码只存强哈希（bcrypt / argon2），禁止 MD5/SHA1 或加盐拼接。
2. 手机号、验证码不得出现在应用日志与慢查询日志的明文里；必要处脱敏（`138****8000`）。
3. 验证码有效期与发送频次（PRD 5.1：60 秒 1 次、5 分钟有效、单号单日 10 次）必须以**数据库原子操作**判断（02 §2.4 明确 P0 不用 Redis），不得依赖内存计数。
4. 登录失败次数（B 端连续 5 次锁定 15 分钟）同样落库计数，不能用本地缓存承载安全边界。
5. 数据库账号按最小权限分配：应用账号无 `DROP`/`GRANT` 权限；报表或运维只读用只读账号。
6. 生产数据不得直接导出到开发/测试环境；造数据用脱敏副本或工厂脚本。
7. 手机号存储已确认（Q18）：应用层 AES-GCM 密文 + HMAC-SHA256 盲索引；唯一索引落 `phone_hash`，登录按 hash 精确查，注销时两列置 NULL 释放手机号。

## 12. 禁止项

- 用 ORM 自动生成表结构代替迁移脚本（MyBatis-Plus 只做 CRUD，不做 DDL）
- 物理外键、物理删除题目与学员、硬删操作日志
- `SELECT *`、无条件 `UPDATE`/`DELETE`（必须带 `WHERE`）
- 在字段里存逗号拼接数组或 JSON 代替关联表（确需时先评审并说明查询方式）
- 用 `FLOAT` 存得分/正确率、用 `TIMESTAMP` 存时间、用 `ENUM` 存状态
- 字段注释只写"状态"而不写取值含义
- 迁移脚本夹带业务数据刷写而不注释说明
- 引入 Redis 相关设计（P0 已明确不用），或把验证码/登录锁定做成内存态
- 依赖 MyBatis-Plus 的"自动逻辑删除"黑盒（02 §2.3 明确不启用），删除语义必须显式

## 14. SQL 编写规范

**查询（DQL）**

1. 只查需要的列，禁止 `SELECT *`（含 ORM 生成的）。
2. 多表关联必须显式写 `JOIN ... ON`，禁止逗号连接的隐式关联。
3. 分页查询必须带确定性排序（`ORDER BY id` 兜底），否则翻页会重复或漏行。
4. `IN` 列表长度上限 500，超出改分批或临时表。
5. `COUNT(*)` 用于精确计数；大表列表页的"总数"如非必需，允许只返回"是否还有下一页"。
6. 禁止在 `WHERE` 中对索引列做运算：`WHERE DATE(created_at) = ?` 改为范围查询。

**写入（DML）**

1. 批量插入单次不超过 500 行；更大的分批提交，每批独立事务并记录进度。
2. `UPDATE` / `DELETE` 必须带 `WHERE`，执行前先用同条件 `SELECT COUNT(*)` 确认影响范围。
3. 批量更新禁止 `WHERE id IN (...)` 超大列表，改用临时表关联或分批。
4. 不在业务代码里拼 SQL 字符串；MyBatis 一律用 `#{}` 参数绑定，`${}` 仅允许用于已白名单校验的排序字段。

**DDL**

1. 建表语句必须显式指定 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`。
2. 每个字段必须有 `COMMENT`，每张表必须有表注释。
3. 加索引必须评估锁表时间；大表在业务低峰执行，或使用在线 DDL 工具。
4. 禁止在迁移脚本中使用 `DROP DATABASE`、`TRUNCATE`（除种子数据重置脚本并单独评审）。

## 15. 评审清单

### 15.1 DDL 评审清单

- [ ] 表名、字段名符合第 2 章命名规范
- [ ] 主键、`created_at`、`updated_at` 齐全；内容型表有 `created_by` / `updated_by`
- [ ] 所有字段 `NOT NULL` 且有默认值（或明确说明为何允许 `NULL`）
- [ ] 字段类型符合第 4 章，无 `FLOAT` / `TIMESTAMP` / `ENUM`
- [ ] 表注释、字段注释完整，枚举字段注明取值
- [ ] 每个外键列都有索引；业务唯一性有唯一索引
- [ ] 唯一索引已考虑软删除/注销场景（`NULL` 或状态列参与）
- [ ] 索引总数 ≤ 5，每个索引能对应到具体查询
